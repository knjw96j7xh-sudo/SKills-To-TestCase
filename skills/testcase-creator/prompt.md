# 用例生成 Skill — testcase-creator

> 先确认输入，不自动导入，不生成自动化测试代码；检查点和评审点可随项目经验持续沉淀。

---

## 0. 初始化检查（每次触发自动执行）

1. 检查 `.testcase-assets/checkpoints-index.md` 是否存在：
   - 存在 → 继续
   - 不存在 → 提示用户创建并**中止流程**。
2. 检查 `.testcase-assets/review-expectations-index.md` 是否存在，同上。
3. 读取 `.testcase-assets/project.config.md`（若存在），从中载入以下上下文，后续流程无需再次询问用户：
   - 项目名称、项目英文标识（用于文件命名）
   - 业务域列表（用于检查点分类匹配）
   - 常用导出路径
   - 默认优先级规则、评审默认应用维度
4. **配置校验（强制阻断）**：检查 `project.config.md` 是否包含 `[填写` 开头的占位符。若检测到任何占位符，**直接中止流程**，输出：
   ```
   [BLOCK] project.config.md 中存在未填写的占位符，无法继续：
     - [填写项目中文名] → 请替换为实际项目名称
     - [填写英文缩写] → 请替换为实际英文标识
     - [填写姓名] → 请替换为测试负责人姓名
     - [填写团队共享路径] → 请替换为实际共享路径
   请先完善配置，再重新触发 /testcase-creator。
   ```
   **不提供「是否继续」选项，必须填写完整后才能进入阶段 1。**
5. 初始化通过后，输出：

```
[OK] 资产加载成功
[DIR] 检查点索引：.testcase-assets/checkpoints-index.md
[DIR] 评审点索引：.testcase-assets/review-expectations-index.md
[DIR] 项目配置：.testcase-assets/project.config.md（已载入上下文）
>> 开始用例生成流程，共 5 个阶段，每步需您确认后继续。
```

> **Token 追踪**：本次运行将在每个阶段结束时记录 token 消耗，阶段 5 输出全阶段汇总对比表，用于验证评审优化的实际效果。

## 1. 需求与设计输入（阶段 1/5）

**提示用户：**

```
【阶段 1 — 需求与设计输入】
请提供需求来源（选择一种或多种）：
  A. 直接粘贴文字需求描述
  B. 乐享页面链接（我将读取内容）
  C. 接口文档链接或本地接口文档文件路径
  D. 本地技术方案文件路径（.md / .docx / .pdf）
  E. 图片/截图（.png / .jpg / .jpeg / .gif / .webp）
  F. 飞书文档链接
  G. Excel 需求列表（.xlsx / .xls）
  H. 需求管理工具链接（Jira / Tapd / 禅道）

设计稿请先导出为 PDF（选择 D）或图片（选择 E），可与其他需求来源组合提供（如 A,D）。
请输入来源类型（A-H）并提供对应内容：
```

**收到输入后执行：**
- 若为 B-H 类型，读取对应链接或文件内容：
  - `.pdf`：`pdftotext '<路径>' -`（macOS/Linux/WSL）或 Windows 原生：`python3 -m pdfplumber --text '<路径>'`
  - `.docx`：`textutil -convert txt -stdout '<路径>'`（macOS）或 `python3 -c "import docx; d=docx.Document('<路径>'); print('\n'.join(p.text for p in d.paragraphs if p.text))"`（Windows，需 `pip install python-docx`）
  - `.md`：直接使用 Read 工具
  - `.xlsx` / `.xls`：`python3 -c "import openpyxl; wb=openpyxl.load_workbook('<路径>'); [print('\t'.join(str(c.value or '') for c in row)) for ws in wb.worksheets for row in ws.iter_rows()]"`（需 `pip install openpyxl`）
  - 图片（.png/.jpg/.jpeg/.gif/.webp）：使用 Read 工具直接读取，自动识别图片中的需求内容
  - 飞书文档链接（`feishu.cn` / `larksuite.com`）：使用 WebFetch 工具读取
  - 需求管理工具链接（Jira / Tapd / 禅道）：使用 WebFetch 工具读取；API 链接可使用 Bash + curl
  - 设计稿 PDF：除提取文字外，还需渲染并查看用户指定页或相关页面，不得仅依赖文本层判断布局与交互
- 多来源输入必须保留来源归属并合并分析，不得用设计稿内容覆盖文字需求。需求与设计稿同时存在时，交叉检查字段、文案、交互、状态和业务规则是否一致
- 提取并输出以下结构；未提供设计稿时省略“设计稿分析”和“需求与设计差异”：

```markdown
##  需求与设计解析结果（请确认）

- **测试对象**：[功能名称/模块]
- **业务规则**：
  1. [规则1]
  2. [规则2]
- **限制条件**：[如：仅限已登录用户、金额 ≥ 0.01 元]
- **接口/端点**：[如有]
- **涉及角色**：[如：普通用户、管理员]

### 设计稿分析

- **设计范围**：[文件 / 页面 / 画板 / 节点名称]
- **页面与流程**：[入口、页面流转、关键操作路径]
- **组件与字段**：[表单项、按钮、列表、弹窗等]
- **交互与状态**：[默认/加载/空/禁用/错误/成功等状态]
- **视觉与适配**：[层级、间距、颜色、字号、响应式/多端差异]
- **校验与反馈**：[输入约束、错误文案、操作反馈]

### 需求与设计差异

| 类型 | 需求描述 | 设计表现 | 影响/待确认项 |
|------|----------|------------|---------------|
| 缺失/冲突/补充 | [需求内容] | [设计内容] | [测试影响或需产品确认的问题] |

[OK] 若以上解析正确，请回复「确认」继续阶段 2。
[FAIL] 若需修正，请指出错误内容后重新确认。
```

**用户确认后**，执行以下操作：
1. 提取「测试对象」作为模块名（取简短关键词，如"碳盘查清单"、"用户中心"）
2. **模块名清理**：移除文件系统不允许的字符（`/ \ : * ? " < > |`），替换为空格或下划线
3. 创建本次运行的子目录：`.testcase-assets/history/<YYYYMMDD>_<HHMMSS>_<模块名>/`
4. 后续所有文件均写入此子目录

> **[TOKEN] 阶段 1 完成**：记录当前终端累计 token 值（`累计: XXX`），作为阶段 1 结束基线。

## 3. 用例生成（阶段 3/5）

**触发条件**：用户回复「生成用例」后执行

**执行步骤：**

1. **读取列配置**：读取 `.testcase-assets/templates/testcase-table-config.json`，获取 `columns`（必填列）和 `optional_columns`（可选列）。若文件不存在，使用默认 9 列（用例ID/所属模块/测试点/前置条件/操作步骤/预期结果/关联检查点/场景类型/优先级）。单模块需求的「所属模块」统一填写测试对象，多模块需求填写用例对应的子模块。

2. **用户自定义列（可选）**：若用户主动要求增加可选列（如「加上执行人」「加上自动化标记」），从 `optional_columns` 中选取对应列加入表头。

   **备注列强制规则**：若输出格式包含「备注」列，该列所有生成用例必须留空。不得自动写入来源用例 ID、历史备注、评审结论、检查点说明、追踪信息或其他辅助文本；需要保留的过程信息写入评审报告或运行目录内的审计文件，不得写入用例备注。

3. 基于需求要素 + 设计稿要素（如有）+ 已选检查点，拆分测试点（内部推理，无需展示）。必须覆盖设计中明确呈现的页面流程、组件字段、交互状态、视觉适配与校验反馈；差异项在确认前不得擅自选定需求或设计为准
4. 生成测试用例表：

```markdown
##  测试用例表（初稿）

| 用例ID | 所属模块 | 测试点 | 前置条件 | 操作步骤 | 预期结果 | 关联检查点 | 场景类型 | 优先级 |
|--------|----------|--------|----------|----------|----------|------------|----------|--------|
| TC-001 | 用户中心 | 正常找回密码 | 用户已注册 | 1.输入手机号 2.获取验证码 3.输入新密码 | 密码修改成功，跳转登录页 | UC-01 | 正向 | P1 |
| TC-002 | 用户中心 | 手机号格式错误 | 无 | 输入10位手机号点击发送 | 提示"请输入正确手机号" | UC-01 | 异常 | P0 |
| TC-003 | 用户中心 | 验证码60秒内重发 | 已发送一次验证码 | 60秒内再次点击发送 | 按鈕置灰，倒计时展示 | UC-02 | 边界 | P1 |
| TC-004 | 用户中心 | 并发提交密码重置 | 两个会话同时操作 | 同时提交两个重置请求 | 只有一个成功，另一个提示失效 | RISK-01 | 并发 | P2 |

> 共生成 X 条用例，覆盖正向 X / 异常 X / 边界 X / 并发 X 条

[OK] 请回复「进入评审」进入阶段 4，或直接告诉我需要修改的用例编号和修改内容。
```

3. 将用例表写入 `.testcase-assets/history/<运行目录>/1-评审记要.md`

> **[TOKEN] 阶段 3 完成**：记录当前终端累计 token 值（`累计: XXX`），作为阶段 3 结束基线。

## 4. 评审优化（阶段 4/5）

**触发条件**：用户回复「进入评审」后执行

**执行步骤：**

### 4.1 评审维度选择

1. 读取 `.testcase-assets/review-expectations-index.md`，**按分类展示所有评审点**：

```
【阶段 4 — 评审点选择】
读取评审点索引，请选择本次评审要重点关注的维度：

>> 用户体验
  [UX-01] 操作失败有明确错误提示
  [UX-02] 关键操作有二次确认弹窗

 数据一致性
  [DATA-01] 写操作后读取结果与预期一致
  [DATA-02] 跨模块数据联动正确性

[BUG] 历史易错点
  [BUG-01] 切换账号后缓存未清除
  [BUG-02] 弱网下接口超时无兜底提示

 完整性
  [COMP-01] 所有业务规则均有对应用例
  [COMP-02] 接口入参边界值已覆盖

[NOTE] 请输入评审点编号（多个用逗号分隔），或输入「全部」应用所有评审点：
```

收到选择后，将选中的评审点按分类（如 UX、DATA、COMP、EXEC、BUG、SEC、PERF）分组。

### 4.2 评审范围确定

2. **确定本轮评审范围**（主 agent 跟踪 `review_round`，初始为 1）：

- **第 1 轮**：全量评审，所有用例参与审查。
- **第 2 轮及之后**（增量评审）：
  - 将用例表拆分为「已有用例」和「本轮新增/修改用例」
  - 「已有用例」仅列出 `用例ID + 测试点 + 场景类型 + 优先级`（不展开前置条件、操作步骤、预期结果）
  - 「本轮新增/修改用例」展示完整行信息
  - subagent 仅需评审新增/修改的部分，已有用例作为上下文参考

### 4.3 并行分维度评审

3. **按维度启动并行 subagent**（每个维度 1 个 subagent，所有 subagent 同时执行）：

   将选中的评审点按分类（如 UX、DATA、COMP 等）分组。**每组启动 1 个独立 subagent**，仅关注该维度的评审点。

   - 每个 subagent 独立接收：需求与设计要素摘要 + 用例表（全量或增量）+ 仅其维度的评审点
   - 各 subagent 互不可见，各自聚焦单维度深度审查
   - 主 agent 等待所有 subagent 完成后，合并各维度报告

   > **为什么按维度分并行**：单 agent 同时审 7 个维度时信息量大、注意力分散。按维度拆分后，每个 subagent 只关注 1 个维度，审查深度更高、遗漏更少。同时并行执行，总耗时约等于最慢维度的时间。

   **subagent prompt 模板**（每个维度独立，维度名称从 review-expectations-index.md 的分类标题提取）：

   ```
   你是一名独立测试评审专家，专注于「{维度名称}」维度的审查。
   请基于以下该维度的评审点，对用例表进行逐条审查。

   ## 需求要素
   [粘贴需求摘要]

   ## 设计稿要素（如有）
   [粘贴设计摘要与已确认的差异处理结论]

   ## 评审维度：{维度名称}
   [仅粘贴该维度的评审点编号和描述，不包含其他维度]

   ## 待评审用例表
   [粘贴用例表 — 第 1 轮为全量，后续轮次为增量（已有用例摘要 + 新增用例详情）]

   请输出：
   1. 评审报告表格（评审点 / 是否已覆盖 / 分析说明 / 建议补充用例）
   2. 建议补充用例表（如有，需包含完整的用例行信息）
   3. {维度名称} 维度评审结论
   ```

   > **注意**：每个 subagent 仅接收其对应维度的评审点列表，不接收其他维度的评审点。这确保每个 subagent 的处理信息量约为原方案的 1/7。

### 4.4 合并评审结果

4. **主 agent 合并各维度评审报告**：

   所有维度 subagent 完成后，主 agent 按以下规则合并：

   | 场景 | 处理方式 |
   |------|----------|
   | 评审点标记 [OK] | 直接采纳，标记为「已覆盖」 |
   | 评审点标记 [FAIL] | 直接采纳，标记为「未覆盖」 |
   | 评审点标记 [WARN] | 采纳，标记为「需关注」 |
   | 不同维度建议相同补充用例 | 去重合并，标注来源维度 |

   合并后生成汇总评审报告，包含：
   - 各维度评审结论汇总
   - 未覆盖评审点清单（按维度分组）
   - 建议补充用例清单（含来源维度标注）

### 4.5 文件输出

5. **写入文件**：

   - **评审报告**：写入 `.testcase-assets/history/<运行目录>/1-评审报告-第N轮.md`（N 为当前轮次，如第1轮、第2轮）
     - 包含：各维度详细评审报告 + 合并结论 + 建议补充用例
     - **Token 统计**（追加到评审报告末尾）：
       ```
       ##  Token 消耗（本轮）
       | 项目 | 数值 |
       |------|------|
       | 评审轮次 | 第 N 轮 |
       | 评审模式 | 全量 / 增量 |
       | 并行维度数 | X 个 |
       | 评审用例数 | X 条 |
       | 本轮 token 消耗 | 约 XXX（本轮结束累计 - 本轮开始基线） |
       | 会话累计 token | XXX |
       ```
   - **用例表更新**：`1-评审记要.md` **仅保留最终用例表**（不含历轮评审记录）
     - 若本轮产生补充用例，追加到用例表中，用例ID 递增

### 4.6 用户决策

6. 主 agent 展示合并后的评审报告，询问用户：

```
评审完成，发现 X 个未覆盖点，建议补充 X 条用例。

请选择操作：
  A. 接受所有补充（含待确认项，合并后继续评审）
  B. 仅接受共识项（忽略待确认项）
  C. 部分接受（指定编号）
  D. 手动修改
  E. 忽略，进入阶段 5

[WARN] 评审是否通过？
  → 若选择 A/B/C/D 将生成优化稿，回到评审循环（review_round += 1，自动启用增量评审）
  → 若选择 E 将进入阶段 5（定稿导入）
```

7. 若选 A/B/C/D：合并补充用例到用例表，`review_round` 递增，返回 4.2（自动进入增量评审模式，仅评审新增/修改用例）。
8. 评审通过后，`1-评审记要.md` 仅保留最终用例表（不含历轮评审记录），评审报告分散在各轮次的 `1-评审报告-第N轮.md` 中。

## 5. 定稿导入（阶段 5/5）

**触发条件**：用户确认评审通过后执行

**执行步骤：**

1. 输出最终定稿用例表（完整版），写入 `.testcase-assets/history/<运行目录>/2-用例定稿.md`

2. 询问导出平台（可多选，逗号分隔）：

```
【阶段 5 — 定稿导出】
[OK] 用例定稿已保存。
```

### 3b. Excel / XMind 导出（若选 E 或 X）

**步骤 A — 序列化用例数据**：将最终用例写入 `.testcase-assets/history/<运行目录>/export_data.json`，格式：

```json
{
  "meta": {
    "project": "<从 project.config.md 读取项目名称>",
    "module": "<本次测试模块名>",
    "generated_at": "<YYYY-MM-DD>"
  },
  "testcases": [
    {
      "id": "TC-001",
      "module": "<所属模块>",
      "test_point": "测试点",
      "precondition": "前置条件",
      "steps": "1. 步骤一\n2. 步骤二",
      "expected": "预期结果",
      "checkpoint": "XX-01",
      "type": "正向",
      "priority": "P1",
      "remark": ""
    }
  ]
}
```

其中 `module` 为每条用例的必填字段；`remark` 对应可选的「备注」列，必须固定写为空字符串。即使原始需求、历史用例或评审报告包含备注，也不得复制到该字段。

当把生成用例替换或合并到已有 Excel 时，只保留非目标模块原有备注；所有新生成用例的备注单元格必须为空，不得使用备注记录来源 ID 或合并追踪信息。

**步骤 A2 — 强制自检 JSON 格式**（必须执行，循环直到通过）：

写入完成后，你必须亲自验证 JSON 格式无误。用以下命令检查：

```bash
python3 -c "import json; json.load(open('.testcase-assets/history/<运行目录>/export_data.json'))" && echo "[OK] JSON valid" || echo "[FAIL] JSON invalid"
```

- 若输出 `[FAIL] JSON invalid`：**你必须**读取错误信息，自行找出 JSON 中的格式问题（单引号、尾逗号、`None`/`True`/`False` 等），修正文件内容后重新写入，然后**再次运行上述命令**，直到输出 `[OK] JSON valid` 为止。
- 若输出 `[OK] JSON valid`：继续下一步。

JSON 格式校验通过后，再强制检查备注字段：

```bash
python3 -c "import json; d=json.load(open('.testcase-assets/history/<运行目录>/export_data.json')); assert all(tc.get('remark', '') == '' for tc in d['testcases']), '生成用例的 remark 必须全部为空'"
```

- 若检查失败：将所有 `testcases[].remark` 修正为 `""` 后重新检查，直到通过。
- 不得通过删除 `remark` 字段规避检查；字段保留，但值固定为空字符串。

> **常见错误自查清单**（按出现频率排序）：
> 1. 字符串用了单引号 `'`（必须全部用双引号 `"`）
> 2. 对象 `}` 或数组 `]` 前有多余逗号
> 3. 中文文本中含未转义的双引号 `"`（须写成 `\"`）
> 4. 误用了 Python 的 `None`、`True`、`False`（应为 `null`、`true`、`false`）
> 5. 文件开头有 BOM 字符（保存时须选 "UTF-8 without BOM"）
> 6. 字符串内包含未转义的真实换行或 Tab（须写成 `\n`、`\t`）
> 7. 反斜杠未转义，如 Windows 路径 `C:\Users`（须写成 `C:\\Users`）
> 8. 数字有前导零，如 `001`（应用引号包裹为 `"001"`）

**步骤 B — 调用导出脚本**：

- 若选 **E**（Excel）：
